# NEON Admin Dashboard

لوحة الإدارة متاحة على المسار:

`/admin`

## المسؤول الأساسي Bootstrap Admin

تسجيل الدخول وحده لا يمنح صلاحية الإدارة. لتعيين المسؤول الأساسي استخدم أحد الخيارات التالية في بيئة الخادم:

- `NEON_ADMIN_EMAILS`
- `NEON_ADMIN_UIDS`
- Firebase claim: `admin: true`
- Firebase claim: `role: "admin"`
- Firebase claim: `role: "super-admin"`

المسؤول الأساسي يعامل كـ `super-admin` وهو محمي من تغيير دوره أو إيقافه من داخل اللوحة لتفادي Lockout إداري.

## الأدوار والصلاحيات RBAC

بعد تفعيل مسؤول أساسي يمكن تفويض المسؤولين الآخرين من تبويب **المستخدمون** داخل `/admin` دون إضافة كل مسؤول جديد إلى متغيرات Railway.

### `super-admin`

- جميع أقسام لوحة الإدارة.
- إدارة بنك الأسئلة والبلاغات والمكرر المحتمل.
- قراءة سجل التدقيق.
- عرض المستخدمين وتفاصيل نشاطهم.
- تغيير الأدوار.
- إيقاف أو إعادة تفعيل الوصول إلى المنصة.

### `content-admin`

- ملخص الإدارة.
- إدارة بنك الأسئلة.
- معالجة البلاغات المرتبطة بالمحتوى.
- كشف المكرر المحتمل.
- قراءة سجل التدقيق.
- لا يملك إدارة المستخدمين أو منح الصلاحيات.

### `support`

- ملخص الإدارة العام.
- عرض المستخدمين وتفاصيل نشاطهم.
- معالجة البلاغات.
- قراءة سجل التدقيق.
- لا يملك فتح أو تعديل بنك الأسئلة.
- لا يملك تغيير الأدوار أو إيقاف الحسابات.

### `student`

لا يملك صلاحية الدخول إلى لوحة الإدارة.

التحقق النهائي من كل Capability يتم على الخادم. إخفاء التبويبات أو الأزرار في الواجهة هو لتحسين تجربة المستخدم فقط وليس طبقة الحماية الأساسية.

## سجل المستخدمين

يستخدم النظام جدول `neon_platform_users` لحفظ:

- Firebase UID.
- البريد والاسم عند توفرهما من جلسة Firebase.
- الدور.
- حالة الوصول `active` أو `suspended`.
- سبب الإيقاف الإداري.
- أول ظهور في المنصة.
- آخر نشاط معروف.
- آخر مسؤول عدل الدور أو الحالة.

عند تشغيل لوحة المستخدمين يتم استيعاب المستخدمين المعروفين مسبقًا من جداول `neon_users` والتقدم والاختبارات حتى لا تبدأ اللوحة فارغة بعد نشر الميزة.

لوحة المستخدم تعرض عند توفر البيانات: الاسم والبريد وUID، الدور والحالة، آخر نشاط، عدد محاولات الاختبارات ومتوسطها، الهدف الدراسي والدرجة المستهدفة، وآخر محاولات الاختبارات.

## إيقاف المستخدم

الإيقاف الحالي هو **Platform-level suspension** وليس تعطيلًا لحساب Firebase Authentication نفسه.

عند تحويل المستخدم إلى `suspended`:

1. `/api/access/session` يرفض الحساب.
2. `ensureAuth()` يمنع استكمال تحميل جلسة الطالب.
3. Access Guard المركزي يمنع الطلبات الموثقة إلى APIs المنصة حتى عند محاولة تجاوز الواجهة.
4. يتم تسجيل الإجراء في `neon_admin_audit`.

يوجد حاجزان ضد القفل الإداري غير المقصود:

- لا يستطيع المسؤول تعديل دوره أو إيقاف حسابه من نفس الجلسة.
- المسؤول الأساسي المعرف في البيئة أو Firebase claim محمي من التعديل داخل اللوحة.

تعطيل المستخدم داخل Firebase Authentication نفسه يتطلب Firebase Admin SDK / صلاحيات خادم مخصصة، ولم يتم الادعاء بتوفيره ضمن هذه المرحلة.

- `dashboard.read`
- `content.read`
- `content.manage`
- `reports.manage`
- `duplicates.read`
- `audit.read`
- `users.read`
- `users.manage`

## نموذج إدارة المحتوى

- ملفات بنك الأسئلة المولدة تظل المصدر الأساسي.
- التصحيح أو الإخفاء أو الاعتماد يُحفظ في PostgreSQL داخل `neon_question_overrides`.
- الخادم يطبق الـOverrides عند تقديم `/data/exams/*.json` للطلاب.
- تغير أي Override يغير `adminRevision` في manifest لإبطال Cache القديم.
- السؤال بحالة `hidden` لا يصل إلى بنك الطالب الفعال.
- إعادة الضبط تحذف الـOverride وتعيد النسخة الأصلية.

## البلاغات وسجل التدقيق

حالات البلاغات: `new`, `reviewing`, `resolved`, `dismissed`.

كل تعديل سؤال، أو إعادة ضبط، أو تغيير حالة بلاغ، أو تغيير دور/حالة مستخدم يسجل داخل `neon_admin_audit` مع UID المسؤول، البريد عند توفره، نوع الإجراء، الكيان المتأثر، الحالة قبل وبعد، والوقت.

## كشف المكرر المحتمل

الفحص مخصص للمراجعة البشرية ولا يحذف الأسئلة تلقائيًا. تتم المقارنة داخل المادة الواحدة مع مراعاة تشابه النص وتوقيع الأرقام لتقليل النتائج الخاطئة.
